# US111 — Generate a Simulation Report

## 1. Requirements

**As a Flight Control Operator, I want to receive a summary of the simulation results so that I can determine if the programmed flights are safe to run.**

### Acceptance Criteria
- The FCO can select a flight plan file from the available test scenarios.
- The FCO can optionally select a weather configuration.
- The system invokes the C simulation executable and waits for it to complete.
- The system displays a summary report including: total flights, total steps, total violations, environment status, global result (PASSED/FAILED), flight execution statuses, and safety violation details.
- The report is saved to the file system at `scomp/sprint3/simulation_report.txt` for future consultation.
- If the simulation fails or the executable is not found, the system displays an appropriate error message.

### Clarifications from the professor

> **Q:** Should the Java system (US111) simply read a file previously generated by the C program running independently, or should the Flight Control Operator be able to trigger the C simulation directly from the Java UI?
> **A:** *"Don't ask the client how to implement the software. Of course the client would be happy with a seamless experience."* — Angelo Martins

> **Q:** Does the generated summary report need to be saved in the Relational Database (NFR08) for future historical consultation, or is it purely a transient file downloaded/saved locally by the operator?
> **A:** *"The user story says that a file should be stored in the file system. I wouldn't call it transient."* — Angelo Martins

These clarifications informed the following design decisions:
- The FCO triggers the simulation directly from the Java UI — a seamless experience with no need to run the C program separately.
- The report is stored in the **file system**, not in the relational database. The professor explicitly stated "a file should be stored in the file system", ruling out database persistence.
- The C program is a self-contained simulation engine that receives a JSON flight plan as input and produces a text report as output. Integrating the C simulation state into the Java domain model would violate the separation between SCOMP and EAPLI and would contradict the professor's guidance that "the simulation must receive the data it needs to simulate" — i.e., the JSON flight plan is the interface between the two systems.

### Design Decisions
- **`SimulationService`** handles OS detection, automatic compilation, process invocation, and report parsing. It is deliberately kept in the application layer — it has no domain logic, only orchestration of an external process.
- **`SimulationReportDTO`** carries the parsed report data to the UI. The UI never touches the file system directly.
- **`ProcessBuilder`** is used to invoke the C executable. On Linux, the working directory is set to `scomp/sprint3/`. On Windows, `wsl --cd <wsl-path>` is prepended to the command, with the Windows path automatically converted to WSL format via `toWslPath()`.
- **Automatic compilation** — `ensureExecutableExists()` runs `make` before the simulation if the executable is absent. This removes the need for manual setup steps.

## 4. Implementation

The FCO selects a flight plan JSON file from `scomp/sprint3/tests/` and optionally a weather CSV from `scomp/sprint3/data/`. The controller enforces authorization and delegates to `SimulationService`. The service ensures the C executable exists (compiling via `make` if needed), then invokes the simulation process. After the process completes, the service reads `scomp/sprint3/simulation_report.txt`, parses it line by line into a `SimulationReportDTO`, and returns it to the controller. The UI displays the summary and the path of the saved report file.
